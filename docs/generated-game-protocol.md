# Agent 生成游戏代码

现有 DSL 继续服务已有玩法。需要新逻辑时，Agent 调用代码构建流程，而不是把新游戏映射成同名比大小。

## 构建链路

1. `agent.py` 判断是否澄清、生成现有 DSL 或进入代码生成。明确要求“使用代码生成”时直接进入构建；其他输入由路由判断，避免旧插件阻止用户切换玩法。
2. `plugin_builder.py` 先让模型输出规则合约和至少三个小牌局单步测试，再独立调用模型写 JavaScript。
3. `plugin_sandbox.py` 执行固定测试、三组种子的完整对局和重复重放，检查牌张守恒、合法动作、结束状态等结构约束。
4. 失败记录回传给编码模型，最多修复两次。修复只能改源码，不能修改本次已经确定的合约和测试。未通过就返回错误，不提供可玩提案。
5. `plugin_engine.py` 将通过测试的插件接到既有确认、模拟、试玩、电脑动作和 SQLite 恢复链路。

测试通过按完整协议和源码缓存。客户端直接提交代码到创建牌局接口，也必须经过相同测试门槛。新源码或新合约会得到不同缓存键。

## 程序接口

源码为返回对象的 JavaScript 表达式，例如 `(() => { /* helper functions */ return {setup, actions, step}; })()`。没有预设的抽乌龟执行器。

- `setup(deck, playerCount, cards)`：接收宿主洗好的牌ID数组和牌面目录，返回初始状态。
- `actions(state, cards)`：列出当前所有合法动作，每个动作有唯一ID、可见标签和可选的抽牌目标位置。
- `step(state, action, cards)`：执行一个合法动作，返回完整新状态。

状态包含 `hands/deck/discard/current_player/finished/winners/scores/phase/data`。所有牌必须始终恰好位于一个牌区；消除牌必须进入discard。扩展游戏状态放在data里，每次调用都会创建新的VM，不允许依赖未保存的全局变量。

只有JSON进入和离开VM，生成代码不进入浏览器，不作为Python执行。前端只渲染平台组件和纸牌素材。抽牌位置的公开ID和标签由平台重新生成，真实手牌和内部状态保存在服务端。

## 执行限制

复用 [quickjs-ng Python wrapper](https://github.com/genotrance/quickjs-ng)，固定版本在uv.lock。独立Python子进程使用`-I`启动，不继承API密钥环境变量；QuickJS没有注册文件、网络、Shell、Python回调或模块加载器。

- 单个VM内存32MB，栈512KB，单次JS调用CPU限时0.2秒。
- 普通操作子进程墙钟3秒，完整模拟12秒；超时杀掉子进程。
- 源码最多40000字符，状态输出和轨迹有大小上限；动作最多256个，完整对局最多600步。
- `Math.random`和`Date`不可用；随机发牌由宿主固定种子提供。源码可用显式保存在state.data中的确定性随机状态。

这是有资源限制且没有宿主能力的JS执行环境，不等同于抵御原生VM漏洞的操作系统沙箱。仍是本机单用户demo，不应据此直接开放公网执行陌生人上传的程序。

## 可见进度与持久化

网页通过`POST /api/agent/jobs`创建后台任务，GET轮询阶段进度。生成代码使用SDK流式读取，但只在完整结束并解析、验证后使用。模型请求提供低思考强度提示和12000 token输出上限。输出上限先使用max_tokens，服务明确拒绝时保留上限改用max_completion_tokens；可选参数重试均显示原因，不限定服务商或模型名。浏览器保存任务ID，刷新后继续轮询；任务本身仅驻留后端内存，后端重启后会明确要求重新生成。

已生成协议和源码保存在浏览器草稿；开始游戏后与完整状态一起保存到SQLite，可在后端重启后恢复。玩家动作在副本上执行，失败不提交状态、事件或revision。

## 验证的边界

行为测试在编码前生成，但仍由模型制定，可能与用户本意一起理解错误。通过这些测试不能证明任意玩法准确。抽乌龟另外使用 `scripts/verify_old_maid.py` 的独立逻辑核对实际轨迹；它不被生成器或运行时调用，也不提供给模型作为实现模板。

当前通用UI覆盖固定2至4人、单局、牌区和合法动作按钮。任意页面布局、实时游戏、多人联网、外部依赖、离线插件导出不在本轮范围内。复杂牌型、下注等没有经过此次验收，不能因为支持自动编码就宣称都能可靠生成。

## 初期实际验证记录（历史失败，后续结果见下文）

使用系统凭据库中的现有 Key，分别通过保存的中转服务实际调用 gpt-5.5 和 gpt-6-astra，没有将 Key 写入代码或报告。

- 实际模型返回过规则合约与 JavaScript 源码；构建器运行了源码并暴露测试失败，但尚未获得通过全部检查的抽乌龟提案。
- 发现并修复：动作 ID 与测试 ID 格式不一致、错误反馈缺少合法 ID、点分路径测试预期重复牌未提前拦截、切换玩法被旧插件直接路由锁住。
- 原始模型合约还存在语义错误，例如手中剩两张却断言仅剩一张的终局。结构检查不等于语义正确，独立规则核对仍是必要验收。
- 最近一次真实请求原始错误为 APIError: `The service is busy. Please retry later.`（93.23秒）；原来的通用错误掩盖了原因，现已保留脱敏后的流内服务错误。
- 浏览器实际点击验证：保存新模型且保留原 Key、输入完整抽乌龟规则、发送后台生成、刷新恢复任务及原输入、生成失败后允许重试。没有点击完成真实生成的抽乌龟整局，因为没有可玩提案。
- 独立验收脚本 `scripts/verify_old_maid.py` 和同色变体选项已经编写，尚无成功真实产物可供验收；不能用协议单测中的手写样例代替。

后续验收顺序：抽乌龟真实生成 → 独立五种子逐步核对 → 浏览器整局及恢复 → 自然语言修改为同点同色配对 → 再次独立核对和浏览器整局。通过前保持实验状态。

## deepseek-v4-flash 实际验收

使用用户重新保存的服务与凭据，通过浏览器自然语言对话生成了完整51张牌的两人抽乌龟，随后实际确认、模拟、抽牌至结算。这里复用了QuickJS运行环境和现有纸牌素材，游戏源码由真实模型生成。

- 第一次规则测试存在非法牌，被构建器拦截，模型重新制定测试后生成源码并通过固定案例、三种子完整模拟与确定性重放。
- 独立规则检查另用种子2/11/41/89/133逐步核对，共9/7/4/9/10步，均正确结束。检查交替发完51张牌、同点对子消除、抽取指定位置、回合轮换及最后持Q者输。
- 浏览器实际点击3次抽牌，中间刷新恢复，对手由电脑自动行动；最终我方剩梅花Q、电脑空手获胜1分，共7个事件。
- 原规则文案误写“最后剩黑桃Q”，但QS已被移除；通过自然语言要求Agent仅修正说明，现已改为“一张Q，不限定花色”。原源码SHA256和固定测试完全不变，并重新通过验证与SQLite保存。新版本已开好一局供用户试玩。
- 修正文案时两次重写源码返回finish_reason=length。根据 [DeepSeek官方文档](https://api-docs.deepseek.com/quick_start/agent_integrations/oh_my_pi/) 补充max_tokens兼容处理；此改动后的那次源码重试仍被截断，不能声称单靠参数修改已经消除截断问题。
- 因此增加“仅修改说明时复用原源码”：模型明确选择reuse_source时，仅允许title/description/requirements变化，其他执行字段及固定测试必须完全相同；重新运行所有验证，并向用户说明代码没有重写。实际文案修正通过此路径成功。

当前120项自动测试通过。验收汇总为 benchmarks/generated-games-acceptance.json；实际生成的合约/源码保存在 benchmarks/generated-old-maid.json，仅用于复现验收，不被生产生成器加载为模板。可运行：

```powershell
uv run python -X utf8 scripts/verify_old_maid.py benchmarks/generated-old-maid.json
```

这证明这一份抽乌龟产物可执行，不能证明任意玩法或每次生成都成功。同点同色变体、斗地主、桥牌、德州扑克仍待独立验收，代码生成仍保持实验状态。
