# 当前开发问题与优先级

本文按 2026-09-08 的代码、测试和已有验收记录整理。这里的“问题”既包括已确认的产品缺口，也包括会影响继续开发的工程风险；不把尚未复现的猜测写成缺陷。

## 优先级判断

| 优先级 | 含义 |
| --- | --- |
| P0 | 阻止本机 demo 启动或造成数据/安全事故 |
| P1 | 影响核心可信度、扩展能力或后续上线，建议优先处理 |
| P2 | 明确的产品缺口或维护成本，按路线图安排 |
| P3 | 体验、文档或工程效率改进 |

当前没有代码证据表明存在 P0 级线上故障；核心测试和前端构建可以通过。主要风险集中在代码生成可信度、部署边界和功能覆盖。

## P1：生成玩法的语义可信度仍不足

### 当前实现进度（2026-09-08）

- 已将生成结果拆分为“固定场景”“平台独立属性”“人工独立 oracle”“浏览器整局”四类状态；固定场景和属性通过不再被展示为语义正确的证明。
- 规则提案现在先展示由可执行 DSL/合约派生的事实，用户确认后才能进入模拟和试玩。
- 当前只有抽乌龟的人工独立验收记录；没有登记 oracle 的玩法会明确显示 `not_available`，不会伪造通过。
- 本次验证：`uv run pytest -q --basetemp=.test-tmp-current2 -p no:cacheprovider` 为 121 passed；`npm run build --prefix frontend` 通过。

现状：`plugin_builder.py` 会让模型先写行为合约和固定场景，再生成 JavaScript；`plugin_sandbox.py` 会检查牌张守恒、合法动作、完整对局和确定性重放，源码最多修复两次。这个门槛能防止结构性错误，但行为场景本身仍由模型制定，可能与用户真正想要的规则一起理解错误。已有文档也明确说明，抽乌龟的真实产物通过验收不能外推到任意玩法。

影响：用户看到“测试通过”时，容易把它理解为规则正确；复杂牌型、特殊效果和边界条件仍可能漏测。

建议：

1. 把“用户规则 → 可审阅合约”做成独立确认步骤，显示胜负、回合、牌区和特殊效果的可执行定义。
2. 为常见玩法维护人工编写的独立 oracle/golden trace，生成器测试不得使用生成器自己的逻辑作为唯一真值。
3. 扩充属性测试：牌张守恒、可达性、终局必达、动作幂等/重放、不同玩家数和边界牌组。
4. 将“固定测试通过”“独立规则核对通过”“浏览器整局验收通过”拆成不同状态与指标。

## P1：功能覆盖仍停留在有限规则原语

### 当前实现进度（2026-09-08）

- 新增能力矩阵接口 `/api/capabilities`，区分 stable、experimental、planned。
- Agent 提示词和前端提示均明确：代码生成是实验能力，不能把下注、组合牌型、叫牌、阵营、联网同步等需求降级为比大小。
- 下一批规则族仍需逐个增加 schema、状态机、人工 oracle、浏览器验收和对应 UI；增加游戏名称本身不算支持。

现状：固定 DSL 支持阶段动作、摸牌/出牌/弃牌/跳过以及最高牌/手牌数计分；内置规则族覆盖 24 点、无下注 21 点和接牌基础变体。多人联网、下注/筹码、组合牌型、叫牌/阵营、边池、实时同步等未实现或未验收。

影响：项目名称容易让使用者联想到完整扑克平台，但当前产品定位更接近“纸牌规则实验台”。自然语言入口必须持续拒绝超出能力边界的要求，避免错误降级成同名比大小。

建议：先确定下一批明确支持的规则族，并为每个规则族定义 schema、状态机、独立验收集和 UI 需求；不要以增加游戏标题或提示词来替代执行机制。

## P1：部署模型限制扩展到多人或公网

现状：应用只面向本机单用户、单进程；FastAPI 使用单一运行进程，代码生成后台线程池最多一个并发任务；牌局和配置写入本机 SQLite；没有登录、租户隔离、房间服务、跨进程锁或任务队列。

影响：直接启动多个 worker、放到公网或让多个用户共享数据目录，可能出现任务状态丢失、会话互相可见、SQLite 写入竞争或凭据边界不清等问题。生成任务只在后端内存中保存，后端重启后需要重新生成。

建议：若要产品化，先拆分身份/租户、牌局存储、任务队列和实时通道，再决定 PostgreSQL/Redis 等基础设施；在此之前应在启动检查或 README 中明确禁止多 worker 和共享部署。

## P1：QuickJS 隔离不是操作系统级沙箱

现状：生成代码在 `python -I` 子进程和 QuickJS 中执行，限制了网络、文件、Shell、模块加载器、随机源和 CPU/内存/输出规模，并且不把 API Key 传入子进程。`docs/generated-game-protocol.md` 已明确说明，这不是抵御原生 VM 漏洞的 OS 级隔离。

影响：本机可信用户的实验场景可以接受；一旦开放陌生人上传源码或公网多租户执行，进程逃逸、资源耗尽和供应链风险需要更强的隔离层。

建议：公网场景使用容器/沙箱运行时、系统级资源配额、只读文件系统、网络默认拒绝、独立低权限账户和审计；同时保留源码审核与大小/步数上限。

## P2：离线导出与在线执行能力不一致

现状：`exporting.py` 只为 v0.1 编译有限固定决策树，最多 2000 个节点；算式、21 点、接牌和插件玩法只能本机网页执行，页面会提示暂不支持离线导出。

影响：用户可能认为“能试玩”就等于“能下载独立游戏”；新版玩法无法带走或脱离后端复现。

建议：短期在 UI 和 API 错误中继续明确能力矩阵；中期设计版本化离线运行时，或明确把导出定位为 v0.1 练习包而不是通用编译产物。

## P2：模型服务可靠性与可观测性不足

现状：`llm.py` 已处理超时、连接错误、HTTP 错误、流式提前结束、输出过长，以及 `max_tokens`/`max_completion_tokens`/`reasoning_effort` 的兼容回退；但生成依赖外部模型，真实验收记录中出现过 401、502、503、服务繁忙、模型不存在和输出截断。当前只在前端显示脱敏后的错误和后台进度，缺少持久化请求指标与统一重试策略。

影响：问题定位依赖人工复现；用户难以区分上游暂时不可用、配置错误、模型能力不足和规则本身生成失败。

建议：记录请求耗时、模型、状态码、finish reason、重试次数和任务阶段（严禁记录 Key/完整提示词）；对可重试错误采用有上限的退避；为不同模型保存成功率和平均耗时指标。

## P2：SQLite 数据模型尚无显式迁移策略

现状：`configuration` 与 `sessions` 表通过 `CREATE TABLE IF NOT EXISTS` 初始化，牌局 payload 以 JSON 保存；没有 schema 版本、迁移脚本或旧 payload 兼容矩阵。

影响：增加字段、改变规则 schema 或调整序列化结构时，旧数据库只能依赖运行时兼容代码；未来升级可能在启动或恢复牌局时失败。

建议：增加数据库 schema 版本表和有序迁移；为运行时 payload 保存 `engine_version`/`schema_version`；补充旧版本 fixture、迁移回滚和损坏数据诊断。

## P3：测试在受限 Windows 环境中的可移植性

现状：本次验证使用项目内 `UV_CACHE_DIR` 和 `--basetemp` 后得到 120 passed；未设置时，uv 全局缓存和 pytest 默认临时目录可能因权限不足而失败。导入 `pocker_agent.api` 还会立即创建默认应用和数据库，增加了测试对用户目录可写性的依赖。

影响：开发者可能把环境权限问题误判为业务回归，CI/新机器上的首轮体验不稳定。

建议：让测试入口显式设置临时目录；避免模块导入时创建持久化应用，改为 uvicorn factory 或延迟初始化；增加 Windows CI，覆盖无权限默认目录、空 keyring 和数据库重启恢复。

## P3：文档、验收数字和版本状态需要单一来源

现状：`README.md`、`PROJECT.md`、`docs/review-and-acceptance.md` 和 `docs/generated-game-protocol.md` 分别记录了不同阶段的测试数量、玩法状态和历史失败。历史记录有价值，但读者容易把旧的“开发中/未通过”与当前抽乌龟已验收产物混在一起。

建议：在 `PROJECT.md` 保留当前状态快照，在验收文档保留不可变历史；每次发布只从一个脚本或 CI 产出测试数量和支持矩阵，并为历史章节标注日期与“已被后续结果更新”。

## 建议的开发顺序

1. 先固定产品边界：单机实验台还是多人产品，并据此决定是否投入身份、房间和服务端基础设施。
2. 在继续扩充生成玩法前，建立独立规则 oracle、可审阅合约和更强的属性测试。
3. 把模型请求观测、任务失败分类和数据库迁移补齐，降低后续调试成本。
4. 再选择一个复杂玩法做完整纵向切片：schema/状态机、API、UI、模拟、恢复、独立验收和文档同步。
5. 最后评估通用离线运行时和更强代码沙箱，避免在线与导出、实验与公网之间继续扩大差距。
